# Load test results, 23 October 2026

How much of the dinner rush one server handles, and what runs out first. Every number below comes from the run folders next to this file.

## The answer

On one **AWS m7g.large** (2 ARM vCPUs, 8 GB of memory), with the dataset from the indexes lesson (20,000 restaurants, 2 million dishes):

| Traffic | The server keeps up with | Requests a second at that point |
| --- | --- | --- |
| Customers only | **25 orders a second** (1.5× the dinner peak) | about 460 |
| Customers at the dinner peak (1×), plus restaurant tablets asking for new orders every 10 seconds | **about 6,200 tablets** (of 20,000 restaurants) | about 905 |

"Keeps up" means that for a whole 3-minute step: menus load in under 1 second at p99 (the requirement from the lessons), under 1% of requests fail, and under 1% of customer visits are dropped because the server couldn't take them in time.

In both cases, what runs out is the CPU. The memory, the disk, the network and the test runner all had plenty to spare.

## The setup

| | |
| --- | --- |
| API server | m7g.large, 2 vCPUs (ARM, Graviton3), 7,755 MB of memory, ap-south-1a (Mumbai) |
| Software | Ubuntu 26.04.1 LTS, kernel 7.0, Docker 29.9.2, nginx 1.28.3, Postgres 18.6, the app at commit `922acc4` |
| How it runs | the API server and Postgres in Docker (`compose.prod.yaml`), nginx on the server in front of them, HTTPS with a Let's Encrypt certificate |
| Settings | everything at its default: a database pool of 4 connections (pgx's default on 2 CPUs), Postgres `shared_buffers` 128 MB, nginx with one worker per CPU. nginx's `worker_connections` was 768 (Ubuntu's default) in the first run and 4,096 after it |
| Data | 20,000 restaurants, 1,998,071 dishes, 20,000 restaurant staff, 10,002 customers. The database is 222 MB. Reseeded before every run, so each run starts with no orders |
| Test runner | c7g.large, 2 vCPUs, same zone, k6 v2.3.0, sending to `https://food-api.sys0.in` |

Each run's `env-before.txt` has the full record, including the nginx config.

## What the traffic looks like

1× is the dinner peak from the lessons: 120,000 orders in two hours, about 17 orders a second. Customers arrive at a fixed rate. In each visit, 1 in 10 logs in first, then the app calls `/me`, lists the restaurants near a random spot in Bengaluru, and opens four menus, with a pause of 0.5 to 1.5 seconds between steps. 4 visits in 10 then place an order, pay, and check the order every second until it's paid. That's about 20 requests for each order, the number the lessons use. Tablets, when they're on, take turns asking for their restaurant's paid orders, and accept and ready any they find. `loadtest/README.md` has the details.

## The runs

### 1. Customers only, Ubuntu's default nginx: `2026-10-23-customers-only-nginx-default`

| Step | Requests/s | Menu p50 / p99 | Failed | CPU used (of 2 cores) |
| --- | --- | --- | --- | --- |
| 1× | 313 | 3.9 / 47 ms | 0% | 1.33 |
| 2× | 415 | 1,620 / 2,760 ms | **11.2%** | 1.90 |

At 2×, nginx logged `768 worker_connections are not enough` 152 times and refused connections. Each request through nginx uses two connections, one from the phone and one to the API server, so 768 per worker runs out at about 850 phones. The CPU was nearly full at 2× as well.

### 2. Customers only, nginx at 4,096 connections: `2026-10-23-customers-only-nginx-4096`

| Step | Requests/s | Menu p50 / p99 | Failed | Dropped visits | CPU |
| --- | --- | --- | --- | --- | --- |
| 1× | 313 | 4.0 / 46 ms | 0% | 0 | 1.31 |
| 2× | 465 | 4,165 / 5,303 ms | 0.16% | 2,896 | 1.91 |

No more connection errors, but at 2× the CPU was full. Some payments queued for 10 seconds, longer than the API server's `WriteTimeout`, so it closed those connections (nginx: `upstream prematurely closed connection`, 152 times), and 3% of payments failed.

These two runs also had a bug in the app: the index on `addresses (user_id)` that the indexes lesson asks for was missing, so every `/me` read all 10,002 addresses (76 million rows in the 3 minutes at 1×). Run 3 adds it.

### 3. Customers only, with every index: `2026-10-23-customers-only-all-indexes`

| Step | Requests/s | Menu p50 / p99 | Failed | Dropped visits | CPU (nginx / API / Postgres) |
| --- | --- | --- | --- | --- | --- |
| 1× | 314 | 3.7 / 44 ms | 0% | 0 | 1.32 (0.16 / 0.40 / 0.53) |
| 2× | 469 | 4,158 / 4,956 ms | 0% | 2,807 | 1.91 (0.23 / 0.56 / 0.81) |

With the index, `/me` did 10,713 index scans and no full scans of `addresses`. But the CPU barely changed: reading 10,000 short rows was wasteful, but cheap. The menu index from the indexes lesson works: in every run, `dishes` was read only through its index, never with a full scan.

### 4. The limit for customers: `2026-10-23-customers-only-limit`

Searched between 1× (passed) and 2× (failed), 3 minutes per step:

| Step | Orders/s | Requests/s | Menu p50 / p99 | Dropped visits | CPU | |
| --- | --- | --- | --- | --- | --- | --- |
| 1.5× | 25.5 | 461 | 384 / 695 ms | 0% | 1.83 | passed |
| 1.57× | 26.7 | 466 | 1,316 / 1,847 ms | 1.8% | 1.87 | failed |
| 1.63× | 27.7 | 464 | 1,699 / 2,511 ms | 3.9% | 1.85 | failed |
| 1.75× | 29.8 | 470 | 2,488 / 3,778 ms | 7.6% | 1.89 | failed |

Past about 465 requests a second, the server doesn't get faster. More customers only wait longer, and then visits get dropped. At 1.5× the requirement still holds, but menus have slowed from 4 ms to 384 ms at p50, because requests are waiting for the CPU. So 1× is comfortable, with about a third of the CPU free, and 1.5× is the edge.

### 5. 20,000 tablets every 10 seconds: `2026-10-23-with-tablets-coarse`

At only 0.25× customers, the server already failed: menus took 3,396 ms at p99. The tablets asked 1,833 times a second, and most of the answers were empty. This run used an earlier version of the test, where each poll picked a random restaurant, so two polls could accept the same order and the second got a 409. Its `accept` failures (14.8%) come from that, not from the server. Run 6 uses the fixed version, where tablets take turns.

## What this says about the lessons

- **The process lesson: "under 400 requests a second at the peak, and one ordinary server can handle that."** True. At the dinner peak, the server answered 314 requests a second with every menu under 50 ms at p99, using two thirds of its CPU, and it kept up until about 460 a second.
- **Indexes: without an index, every menu reads all 2 million dishes; with it, about 104 pages.** True. The index was used for every menu, in every run. (An earlier test on a laptop: 109 pages with the index, 18,769 without, and at 200 menus a second without the index, only 14% of requests succeeded.)
- **"Look up near restaurants later, when the app has many restaurants."** The test shows when "later" is. With 20,000 restaurants, `near` reads all of them on every call (153 million rows in 3 minutes at 1×), it's the most expensive request, and it answers with 4,108 restaurants (372 KB) when a phone shows maybe twenty.
- **The reverse proxy lesson's defaults matter.** Ubuntu's nginx stopped at about 2× because of its 768-connection default, not because of our app. The deploy guide now raises it.
- **Tablets asking every few seconds don't scale.** One server can't serve both the dinner peak and 20,000 tablets asking every 10 seconds. It manages about 6,200. That's the case for the live updates module, where the server tells the tablet about a new order instead.

## What to keep in mind

- Each step ran once. We didn't repeat runs, so we don't know yet how much the numbers move from one run to the next. Repeating the limit search a few times would tell us.
- The data is generated: restaurants at random spots in Bengaluru, and short dish names. A real menu, with descriptions and photo links, is bigger than our 6 KB.
- Login includes the fake OTP service's 200–500 ms delay, and payments the fake provider's 1–2 seconds, on purpose. They're why the `login`, `verify` and `pay` rows are slower than the rest.
- The test runner was never the limit. On average it used 0.26 to 0.80 of its 2 cores. Its highest moment was 1.79 cores, in run 1; in every other run it stayed at or under 1.03.
