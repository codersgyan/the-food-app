# Load test, 2026-10-28

One API server, an AWS m7g.2xlarge (8 vCPU, 32 GB, ap-south-1c), runs nginx,
the Go app and Postgres 18 with PostGIS, from `deploy/setup.sh`. A second
server, a c7g.2xlarge (8 vCPU, ap-south-1a), sends the traffic with k6 v2.3.0.
The data is the big seed: 20,000 restaurants, 1,998,071 dishes, 10,000
customers. The only server setting changed from Ubuntu's defaults is nginx's
`worker_connections` (768 to 4,096). Postgres runs with its defaults
(`shared_buffers` 128 MB).

1x is our dinner rush from the lessons: 42.5 visits a second, 17 orders a
second. Each visit logs in once in a while, reads /me, finds nearby
restaurants, opens 4 menus, orders, pays and checks the status. With tablets
on, every restaurant's tablet asks for new orders every 10 s, accepts them and
marks them ready.

A step passes when, for the whole step, the menu's p99 is under 1 s, under 1%
of requests fail, and k6 drops under 1% of the visits. Steps last 3 minutes.

11:25 to 13:26 UTC. **Passed.**

| all requests | 30.2M, about 4,185 a second, 0 failed |

| nginx errors | 0 |

The laptop's ssh to the servers dropped at 12:25. k6 kept running on the
runner, and its summary for the whole 2 hours was collected by hand after it
finished, with the same pass rule as run.sh (so steps.csv's start time,
11:25:00, is rounded). The API server's CPU record is missing from 12:25 to
13:17 (monitor-api.csv, then monitor-api-last-minutes.csv). The Postgres row
counts from 12:25 are empty.

Postgres row counts for the 2 hours: 0 full table reads of dishes (30.1M index
reads), restaurants (9.9M), users and addresses. orders had 122,542 full
table reads and order_items 15,716. These come from the start of the step:
run.sh empties the orders tables before each step, Postgres's statistics then
say they're empty, and until autoanalyze runs (it ran 195 times) the tablets'
query reads the whole small table. With statistics, EXPLAIN on the 733k
orders uses `orders_restaurant_id_status_idx` (6 pages, 0.04 ms).

## What limits the server

The CPU. Near the ceiling the load average was 15 to 16 on 8 cores and the
kernel's CPU pressure was up to 80%. The 8 Postgres connections (pgx's default,
one per CPU) were mostly waiting on the app ("Client"), not the other way
round. About 14% of Postgres's page reads miss its 128 MB of shared buffers,
but they come from the operating system's memory, not the disk (iowait about
0.15 cores).
